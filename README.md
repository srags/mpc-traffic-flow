# Quantifying Controllable Highway Congestion

This repo contains the code, data and results for paper [Toward Controllability-Aware Performance Measures: A Case Study on Controllable Highway Congestion](https://arxiv.org/abs/2608.18510v1). This paper is currently under review at Transportation Research: Part C.

The pipeline has three stages:

1. **Calibrate** a METANET second-order traffic model to a day of field data.
2. **Optimize** a VSL policy against the calibrated model with a nonlinear MPC (using the Pyomo package with IPOPT solver).
3. **Analyze** the gap between the uncontrolled and optimally-controlled simulations. 

Controllable Congestion is defined as

```
delay      = TTS_uncontrolled - TTS_freeflow
delay_opt  = TTS_controlled   - TTS_freeflow
CC (%)     = (delay - delay_opt) / delay * 100
```

where TTS is total time spent (veh-hr). See `run_one_day` in [traffic_flow.results.i24](src/traffic_flow/results/i24.py) for the paper-report implementation.

**Case studies considered.**  (a) A synthetic 10 km bottleneck (4 lanes dropping to 2) swept over peak demand. (b) Ten weekdays of I-24 MOTION data (Nov 21 – Dec 2, 2022), a 5.6 km corridor of 14 segments at 400 m / 10 s resolution.

### Public pipeline API

Use the package entry point for the main workflow functions:

```python
from traffic_flow import (
    load_scenario, load_params, calibrate, optimize, evaluate,
    save_result, load_result,
)
```

Settings and named choices remain in `traffic_flow.config`. Importing the public
API does not load Pyomo, SciPy or Matplotlib. Calibration and MPC solvers are
loaded inside their respective pipeline functions; simulation and saved-policy
evaluation do not need solver imports. Existing submodule imports still work.
`save_result` and `load_result` persist complete numerical run bundles, now used
by the CC scripts and exploratory notebook. The legacy policy helpers have been
removed; callers must remove stale imports of them too.

### Typed configuration choices

Import settings and named choices from `traffic_flow.config`. Dataclass keyword
completion exposes each setting; enums expose the supported named options:

```python
from traffic_flow.config import (
    CalibrationConfig, Study, InitMode, MPCConfig,
    LossMode, RobustOptConfig, CalRef, CalSource,
)

calibration = CalRef(CalSource.FIXED_RAMPS)  # Reference to existing parameters.
dynamic_calibration = CalRef(CalSource.DYNAMIC, interval=90)  # Interval in steps.
calibration_config = CalibrationConfig()  # Nominal fit, unchanged defaults.
robust_config = CalibrationConfig(
    robust_opt=RobustOptConfig(objective_mode=LossMode.MEAN_PLUS_WORST),
)
mpc_config = MPCConfig(
    pred_horizon=45, control_horizon=5,
    init_fixed=(150., InitMode.ADAPTIVE),
)
study = Study.SPEED_LB
```

These illustrate individual choices, **not** a new tuned experiment preset.
`Study` labels an existing results directory; it does not enable or
change constraints in `MPCConfig`. `CalRef` groups a saved-parameter source and
its optional dynamic interval; `CalibrationConfig` instead controls a new fit.
`CalSource` names known parameter directories, not the fitter's ramp behavior.
Custom calibration directory names and dates remain strings. Dataset names
must have an entry in the registry in `inputs/scenario.py`. Named choices serialize to the existing
JSON strings, and old string arguments remain supported. Type hints provide
editor checks; they are not a new runtime configuration validator.

### Loading a scenario

```python
from traffic_flow import load_scenario

scenario = load_scenario("i24", "11_30")
spec = scenario.spec       # Resolved dataset identity, geometry and timing.
traffic = scenario.traffic  # Prepared observations and boundary inputs.
```

The loader reads `rho_hat.npy`, `q_hat.npy` and `lane_mapping.npy` from
`data/i24/i24_11_30/`. The number of rows gives the duration in steps; the number
of columns minus the two boundary cells gives the modeled segment count.
Segment length and sampling period cannot be inferred from these arrays: the
dataset registry supplies 0.4 km and 10 seconds for I-24. The loader converts
seconds to hours and uses the shared preparation function, including the
existing two-sample boundary smoothing. It does not load fitted parameters,
run a solver, or create output directories. Segment/time subsetting is not yet
supported by this entry point; saved scenarios with nonzero start times are
rejected rather than silently misaligned.

Callers no longer construct an `i24()` preset or manually supply dimensions.
`Scenario` contains the loaded traffic and its resolved `ScenarioConfig`;
`ScenarioConfig` alone is metadata, not loaded traffic, and contains no
calibration choice. Select saved parameters separately with `CalRef`; pass it
to `load_params`, not `load_scenario`. `load_params` delegates directly to
`model/parameters.py`: static files remain static, while `params_*` subdirectories
select dynamic blocks at the requested interval. Loading does not create
directories or modify observations.

### Concise experiment workflows

`experiments/cc_run.py` loads observations and saved parameters, optimizes, and
saves a complete run. `experiments/cc_plot.py` loads that bundle and produces the
existing CC tables and two figures:

```python
from traffic_flow.config import CalRef, CalSource, cc_mpc
from traffic_flow import load_scenario, load_params, optimize, save_result, load_result
from traffic_flow.results.policies import run_dir, load_runs

calibration = CalRef(CalSource.FIXED_RAMPS)
scenario = load_scenario("i24", "11_30")
params = load_params(scenario, calibration=calibration)
result = optimize(scenario, params, cc_mpc(scenario.spec))
spec = result.scenario.spec
directory = run_dir(spec, calibration=calibration, config=result.config)
save_result(result, directory)

# A later reporting session needs the bundle, not calibration files.
result = load_result(directory)
```

Pass the same `CalRef` to parameter loading and directory selection. The bundle
stores actual parameter arrays; calibration provenance is currently a directory
selector, not an additional metadata field.

`run_dir(spec, calibration=..., config=..., study=...)` places bundles under
the existing dataset/date/calibration/study layout, followed by
`runs/lb_0_hold_1__<settings-id>/run.npz`, for example. When set, temporal and
spatial bounds appear in the label too: `lb_0_hold_1_temp_0.7_spat_25__<settings-id>`.
The readable labels are not the complete identity: the 16-hex-character ID
includes every scenario metadata field and every MPC setting except `verbose`
and `tee`, including initialization-array shape and contents. Equivalent
numbers such as `0`, `0.0` and `-0.0`, list/tuple choices, and array memory
layouts are normalized. Nonfinite settings and object arrays are rejected.

Lookup creates no directories. Reusing identical settings resolves to the same
destination and a successful save replaces that bundle. This is not versioned
history: the ID does not fingerprint observation or fitted-parameter contents,
even though those actual arrays are captured inside each saved bundle.

For reporting without reconstructing solver settings, import `load_runs` from
`traffic_flow.results.policies` and filter the stored `MPCConfig`:

```python
matches = load_runs(
    "i24", "11_30", calibration=calibration,
    where=lambda config: config.speed_lb == 0,
)
if len(matches) != 1:
    raise ValueError(f"Expected one run, found {len(matches)}. Refine the selection.")
result = matches[0]
```

`load_runs` reads complete bundles once per lookup through `load_result`; it is
not a metadata-only index. It discovers old `speed_lb_*` and new settings-ID
folders in the selected collection, validates dataset/date metadata, and filters
using saved settings rather than filenames. Missing collections return an empty
list; malformed bundles raise instead of being silently skipped. Sweep reports
can use the full list. Single-run reports must reject zero or multiple matches:
an old and a new copy both matching are intentionally not silently deduplicated.

`cc_plot.py` passes the captured inputs and optimization result to `cc_report`,
then calls `print_cc_report` and `save_cc_plots`. It reuses saved baseline and
controlled trajectories, recomputing only the measured-inflow diagnostic.
No calibration reload, policy reevaluation or MPC solve is needed. Outputs
remain `fig_new/optimal_vsl.png` and `fig_new/controlled.png`, with the existing
layouts and color limits. This report currently requires static free-flow speeds.

A bundle is required; legacy `.npy` policies are not silently converted or
optimized. The HTML viewer and older multi-day/constraint
scripts still read legacy files and will not pick up new bundles until migrated
or given an explicit legacy export.

### Complete run persistence

```python
scenario = load_scenario("i24", "11_30")
params = calibrate(scenario, calibration_config)
result = optimize(scenario, params, mpc_config)
save_result(result, output_dir)
```

These four entry points exist. `load_scenario` now reads observations only;
`load_params(scenario, calibration=CalRef(...))` is the alternative to fitting with
`calibrate(scenario, calibration_config)`. Neither loading a scenario nor
resolving its `run_dir` creates directories.

The public `optimize()` now deep-copies its inputs together before running and
returns a `RunResult`: `scenario`, `params`, `config`, and the existing numerical
`OptimizationResult` under `optimization`. This captures independent input
snapshots alongside the raw policy and recomputed trajectories. The lower-level
solver/simulation result formats and `evaluate()` remain unchanged;
`frozen=True` alone does not make arrays or dictionaries immutable.

`save_result(result, output_dir)` writes one compressed `run.npz` archive with schema-versioned JSON
metadata, all prepared traffic arrays, static/dynamic parameter arrays, MPC
settings (including optional initialization controls), the raw VSL and both
simulation results. Numeric arrays retain their dtypes and shapes; reading
does not require pickle. The writer uses a temporary file and replaces the
destination only after compression succeeds. Existing policy/JSON files remain untouched.
One output directory represents one run; a successful repeat save replaces
its `run.npz`. The `run_dir` helper separates numerical configurations, including
speed-bound, hold-length and safety-bound sweeps.

`load_result(output_dir) -> RunResult` restores saved arrays, scalar travel times,
and tuple/list settings using `allow_pickle=False`. It does not reload datasets
or calibrations, rerun simulation/optimization, or write files. It rejects
unsupported schema versions, missing settings and missing required arrays
instead of substituting current defaults or data. A directory containing only
a legacy policy is not a complete run. The CC scripts now use this saved bundle.

Report builders should consume results without fitting or optimizing again;
saving numerical artifacts should not implicitly require plotting.
Preserve existing filenames and
plot styling as each report migrates. Multi-day and constraint-sweep figures
will consume collections of results rather than duplicate the solver pipeline.
Legacy policies contain only the VSL and optional metadata. Their readers still
load referenced calibration files from disk, unlike bundle-based CC reporting.

Legacy JSON sidecars contain `calibration_id` and `calibration_interval` alongside
scenario geometry. These existing artifacts remain on disk, but are not the
complete-run format; `load_result` does not fall back to them. The new format
stores the numerical parameter snapshot directly.

Before replacing experiment implementations, compare generated numeric results
to `4f82654` and preserve each report's baseline convention explicitly. In
particular, the older I-24 reports use measured inflow for the uncontrolled run,
whereas `evaluate_policy` uses a modeled origin/queue and a 150 km/hr baseline.
Those are not interchangeable defaults. Old exploratory notebooks under `old/`
still reference APIs removed before this migration and are reference material.

### Regression checks

Run from the repository root with the project environment activated:

```bash
make test           # Routine checks; excludes the slow real calibration/MPC comparison.
make test-detailed  # Full suite, including new calibration and MPC solves with IPOPT.
```

`make test` covers inferred dimensions/units, explicit calibration selection,
solver failure/retry behavior with mocks, and CC script orchestration.
Result-bundle tests cover exact array preservation, failed-write recovery,
loader round trips, invalid bundles, settings identity, and discovery/filtering
across old and new run folders. CC workflow tests check independent
sweep destinations, use of captured report inputs, and rejection of missing or
ambiguous selections before reporting. Retired policy-format
tests are removed; notebook source checks target its move to the run bundle.
It also compares prepared real inputs and generated simulation trajectories
against Git revision `4f82654`, using the same saved parameters and VSL on both
sides and `rtol=atol=1e-10`. It does not run IPOPT or render figures. Source checks
inspect active scripts and notebook source without executing notebook cells;
archived notebooks are excluded. Temporary-file tests do not write to the
repository's `data/` or `results/`.

For each bundle in the ordinary I-24 11/30 fixed-ramp `runs/` collection, the
suite additionally compares its saved baseline and controlled trajectories to
the simulator from `4f82654`, using exactly its observations, parameters and
controls. Both old and new folder names are discovered; study subdirectories
are outside this optional check's scope. The tolerance is `rtol=atol=1e-10`;
no MPC solve or output-file write is involved. These cases skip when no bundles
are present. Run just these baseline/controlled cases with:

```bash
pytest tests/test_pipeline_baseline.py -k saved_cc_run -q --color=yes
```

This isolates simulation/persistence equivalence, not optimizer equivalence.
Two independently optimized policies need not be identical; a policy difference
alone neither proves a refactor bug nor establishes that the change is harmless.

`make test-detailed` additionally enables
`tests/test_solver_baseline.py::test_real_calibration_and_mpc_match_baseline`.
This refits a small real-data case and reruns MPC for both revisions, comparing
parameters, objectives, policies and recomputed trajectories with
`rtol=1e-6, atol=1e-8`. It requires IPOPT, the I-24 11/28 observations and Git
revision `4f82654`. This is the slow check to run before accepting numerical or
solver refactors. Direct `pytest` runs keep it opt-in via
`MPC_RUN_SOLVER_BASELINE=1`; `make test` explicitly deselects it even if that
variable is set.

Comparison artifacts normally go to pytest temporary directories. For the
real-solver check, `MPC_SOLVER_BASELINE_DIR` can select a fresh output directory;
never point it at `data/`. These comparisons do not establish that every
full-size calibration/MPC run will converge or produce identical solutions.

## 3. Data

### 3.1 I-24 MOTION (`data/i24/`)

One directory per date, `i24_MM_DD`, for ten weekdays: 11_21 – 11_25, 11_28 – 12_02. (11/24 and 11/25 are Thanksgiving and the day after; `cc_analysis.format_date_label` tags them "Holiday" rather than a weekday name.)

Each date directory contains a 1-hour window at 10 s resolution:

| File | Shape | Meaning |
|---|---|---|
| `q_hat.npy` | (360, 16) | Flow, veh/hr. |
| `rho_hat.npy` | (360, 16) | Density, veh/km. |
| `v_hat.npy` | (360, 16) | Speed, km/hr. |
| `lane_mapping.npy` | (16,) | Lanes per segment. |
| `on_ramp_mapping.npy`, `off_ramp_mapping.npy` | (16,) bool | Ramp presence per segment. |

**The 16 columns are 14 modeled segments plus two boundary cells.** Column 0 is the upstream boundary (supplies inflow), column 15 is the downstream boundary (supplies downstream density). All data loading slices `[:, 1:-1]`. 14 segments × 400 m = 5.6 km. Velocity is *derived* as `q_hat / rho_hat` rather than read from `v_hat.npy` — zeros are floored to `1e-3` first to avoid dividing by zero.

### 3.2 Calibrated parameters (`data/i24/<date>/calibration_*/`)

Calibration **output** is saved next to the input data.

- `calibration_static/fixed_ramping` — one parameter set for the whole hour. **This is what every paper figure uses.**
- `calibration_static/time_varying_ramping` — ramp terms allowed to vary. Not used in the paper.
- `calibration_dynamic/` — parameters re-fit every `control_h` steps, stored as `control_h_<N>/params_<i>/`. Only fitted for 11_30.

Each holds `tau.npy`, `K.npy`, `eta_high.npy`, `rho_crit.npy`, `v_free.npy`, `a.npy`, `num_lanes.npy`, `beta_array.npy`, `r_inflow_array.npy` (each shape (14,)), plus the model's own predictions (`v_pred`, `rho_pred`, `q_pred`, `v_sim`) for diagnostics. Parameters are loaded through `load_metanet_params` in `traffic_flow.model.parameters`.

## 4. Running the pipeline

### 4.1 Stage 1 — Calibration

**Notebook:** [experiments/metanet_calibration.ipynb](experiments/metanet_calibration.ipynb)

Set `root_path` (cell 3) to the date you want. `run_calibration` (cell 11) solves one large Pyomo NLP fitting `tau, K, eta_high, rho_crit, v_free, a` per segment, plus ramp terms when `include_ramping=True`. Bounds on those parameters are at [traffic_flow.solvers.calibration](src/traffic_flow/solvers/calibration.py).

### 4.2 Stage 2 — VSL optimization

**Command-line runner:** [experiments/run.py](experiments/run.py) supports both CC
and safety sweeps without editing script constants. It uses the same pipeline
and result-directory helper as the existing runners.

```bash
# Preview first: validates inputs and lists destinations, without solving or saving.
python experiments/run.py --dataset i24 --date 11_30 --dry-run

# CC speed-lower-bound sweep.
python experiments/run.py --mode cc --dataset i24 --date 11_30 \
    --calibration-source fixed_ramps --study speed_lb --speed-lbs 0 40 60

# Safety grid: every temporal/spatial combination (optionally crossed with speed-lbs).
python experiments/run.py --mode safety --dataset i24 --date 11_30 \
    --temporal-values 0.7 0.9 --spatial-values 15 25

# Saved dynamic calibration (does not run calibration).
python experiments/run.py --date 11_30 --calibration-source dynamic --calibration-interval 90

python experiments/run.py --help
```

Defaults: CC mode, I-24 `11_30`, fixed-ramp calibration, and `cc_mpc` settings.
Safety mode defaults to temporal `0.7`, spatial `25`, and initialization fallbacks
`adaptive 120 100 80 60 40`. Unlike `safety_run.py`, the CLI has **no implicit
warm-start file**. To reuse the same historical seed, add:

```bash
--warm-start results_bu/i24/i24_11_30/calibration_static/fixed_ramping/safety_sweep/optimal_vsl_temp0.9_spat25.npy
```

`--warm-start` also accepts a complete-run directory or its `run.npz`; paths are
relative to the working directory. The same seed is reused for every sweep
point, not chained from the preceding solve. Omitting the seed may change
convergence and the solution of this nonconvex problem.

Other overrides include `--pred-horizon`, `--control-horizon`, `--hold-length`,
`--warmup-time`, `--control-zone`, `--control-one-segment`,
`--control-changepoints`, and `--init-fixed` (e.g. `adaptive 120 80`, or `none`
to disable fixed fallbacks). Use `--no-verbose` to hide the progress bar and
`--tee` to show solver output. Horizons/durations are steps, speeds are km/hr,
and segment indices start at zero. Safety bounds require `--mode safety`.
Known calibration-source aliases are `fixed_ramps`, `varying_ramps`, and
`dynamic`; relative custom calibration folders are also accepted.

`--study` is only a folder label: `none`, `speed_lb`, `hold_length`, or
`safety_sweep`. When omitted it is `none` for CC and `safety_sweep` for safety.
New bundles go under `results/`; an identical configuration replaces its
previous bundle after a successful save. No figures are generated. For
`cc_plot.py`, select the same dataset/date/calibration/study and speed bound;
the existing CC report requires static free-flow parameters.

**Main CC workflow:** [experiments/cc_run.py](experiments/cc_run.py) loads a scenario and saved calibration, optimizes, and saves a complete run bundle. [experiments/cc_plot.py](experiments/cc_plot.py) loads its captured inputs and trajectories and saves the two CC figures without optimizing again.

```bash
python experiments/cc_run.py
python experiments/cc_plot.py
```

Keep the dataset/date, calibration, study and speed-lower-bound selections aligned
between the scripts. `cc_plot.py` uses the inputs and trajectories in the selected bundle.
The former [run_controllable_congestion notebook](experiments/archive/run_controllable_congestion.ipynb)
is archived for reference.

**Safety-bound grid:** [experiments/safety_run.py](experiments/safety_run.py) uses
the same load → optimize → save workflow, without plotting:

```bash
python experiments/safety_run.py
```

Edit `TEMPORAL_VALUES` and `SPATIAL_VALUES` at the top to select the grid. Its
defaults match [run_safety_sweep.ipynb](experiments/run_safety_sweep.ipynb): date
`11_30`, fixed-ramp calibration, temporal bound `0.7`, spatial bound `25`, and
adaptive/constant initialization fallbacks. `WARM_START` explicitly selects the
existing `optimal_vsl_temp0.9_spat25.npy` seed, reused independently for every
pair; set it to `None` to omit that seed. New runs are complete bundles under
`safety_sweep/runs/`, with directories chosen by `run_dir` from the saved settings.
The notebook remains unchanged for reference and exploration. Existing
`safety_sweep.py`, `safety_sweep_plots.py`, and I-24 constraint plots still read
legacy `.npy` policies; they do not yet consume these new bundles.

The default CC settings are centralized in `cc_mpc`:

```python
pred_horizon    = 45     # time steps (7.5 min)
control_horizon = 5      # time steps (50 s)
hold_len        = 1
v_fd_penalty    = 1e14
control_zone    = list(range(2, num_segments))   # segments 0-1 stay uncontrolled
control_one_segment = None
```

The other parameters the paper sweeps, all fields of `MPCConfig`:

| Key | Meaning |
|---|---|
| `speed_lb` | Minimum posted speed limit, km/hr. |
| `hold_length` | Steps a speed limit must be held before it may change. |
| `safety_temporal` | Max VSL change between consecutive 10 s steps, km/hr. |
| `safety_spatial` | Max VSL difference between adjacent segments, km/hr. |

The runners write `runs/<readable-settings>__<settings-id>/run.npz` under the
selected result directory (including the study subdirectory when selected).
Existing legacy results retain their `optimal_vsl*.npy` and
optional JSON sidecars for older consumers. They are not accepted as complete
run bundles and are not automatically converted.

The MPC is a nonconvex NLP and IPOPT does **not** reliably converge cold on this problem. `mpc_find_vsl` tries warm starts in a fixed order and falls back:

1. `initialize_vsl` if given (usually a neighboring sweep point's solution),
2. the previous MPC step's solution, shifted forward by `control_horizon`,
3. each constant in `init_fixed` in turn (e.g. `[speed_lb, 100, 120, 140, 150]`),
4. fully cold.


### 4.3 Stage 3 — Analysis and figures

All read the saved VSL policies and run them to determine the controllable congestion %.

| Command | Produces |
|---|---|
| `python experiments/I_24_table_plotting.py` | `figs/i24_cc_table.png`, `.tex`, `figs/i24_avg_delay_bar.png` which summarizes statistics across all 10 days of I-24. |
| `python experiments/I_24_tsd_plotting.py` | `figs/i24_tsd.png` plot time-space diagrams, 11/28 vs 12/02. |
| `python experiments/I_24_constraint_plotting.py` | `figs/i24_constraints.png` (2×2 constraint panel), `figs/i24_safety_heatmap.png`. |
| `python experiments/synthetic_demand_tsd.py` | `figs/synthetic_demand_tsd.png`. |
| `python experiments/synthetic_cc_demand.py` | `figs/synthetic_cc_demand.png` — CC vs peak demand. |

The two synthetic scripts are independent **load → report → plot** entry
points. Their settings are at the top: `PEAKS`, `POLICY_DIR`, `FIGURE_DIR`,
and `CONFIG = SyntheticConfig()`. The shared typed configuration in
`traffic_flow.config` defines the road's lane counts, segment length, time
step, duration, initial speed and demand pulse. Defaults match the existing
10 km, 4-to-2-lane bottleneck study. The heatmap script separately specifies
the blue control-zone marker (`CONTROL_START_KM`), which is not recorded in CSV.

Both scripts now read existing policies from **`results_bu/synthetic_10km/demand`**;
change `POLICY_DIR` explicitly to use another collection. The filenames are
`demand<peak>.0_duration0.5.csv` for the default integer peaks. CSVs contain no
scenario metadata, so the configuration must match the policy-producing run.
No files are copied, converted or written back to that directory. These legacy
replays do not use the I-24-only `load_scenario`/`load_runs` interface or invent
measured trajectories for calibration.

`load_synthetic_results(...)` returns `SyntheticResult` objects containing
the settings, peak, an `OptimizationResult` (policy plus both complete
simulation histories), vehicle/free-flow totals, and computed delay/CC
properties. Both figures retain the previous numerical conventions: modeled
origin/queue, unrestricted no-control speeds, and the **terminal demand sample
included** in vehicle/free-flow totals (721 samples for 720 simulation steps).
This last convention is intentionally preserved, not an exact two-hour
left-endpoint integral. The bar-chart script skips missing policies with a
message; the heatmap script requires every requested peak. An entirely missing
collection or a malformed policy produces a clear error before plotting.
